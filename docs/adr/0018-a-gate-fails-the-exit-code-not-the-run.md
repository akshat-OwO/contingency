# A Gate fails the exit code, not the Run

A Flow may declare a **Gate**: a list of accessibility rule ids that must produce no Finding. With no Gate declared, a Run reports every violation and fails nothing, which is [ADR 0009](./0009-run-execution-semantics.md)'s position unchanged. When a Gate is declared and breached, the Run's outcome stays `completed` and the CLI exits non-zero.

## Consequences

- **Outcome and exit code become separate axes.** ADR 0009 stated flatly that "a Finding never influences a Run's outcome or the CLI's exit code", and tied both to one value. That conflation was safe only while the second question did not exist. A Run that executed every Step and then breached a policy _completed_ — the site failed, not the Run — and `runIsBaselineEligible` keys on outcome, so this keeps a policy-breaching Run eligible as a Baseline. That is the correct answer and the reason for the split: a Run that documents today's known-bad state is exactly what tomorrow should be compared against.
- **Exit codes distinguish the two failures**: `0` completed and within Gate, `1` the Run did not complete, `2` the Run completed and breached its Gate. CI can then tell "the site regressed" from "the check is broken", which one code cannot express.
- **ADR 0009's reasoning survives intact.** Its argument — every real site has pre-existing violations, so failing on Finding count makes the build red on day one and the check gets switched off — is an argument against failing _by default_. The default is still not failing. A Gate is opt-in, names specific rules, and is therefore something an author chose to hold themselves to.
- **The Gate is rule ids, not a severity threshold.** Severity alone is too blunt in both directions: authors want to hold `image-alt` at any severity and to accept an entire rule they have triaged. Severity thresholds and count ceilings are deferred, not rejected.
- **The Gate lives in the Flow, overridable by CLI flag.** Unlike Run artifacts ([ADR 0014](./0014-artifacts-are-run-properties.md)), which are properties of how a Run was invoked, a policy bar is a fact about what is being audited — a checkout Flow and a marketing page are not the same risk, and two Flows in one repository can legitimately hold different bars.
- **A Gate is not a Regression.** A Gate is an absolute bar against a fixed rule list; a Regression is relative to a Baseline. A Run can breach its Gate with no Regression at all — the violation was there yesterday too — and that distinction is what keeps the two signals separately actionable.
