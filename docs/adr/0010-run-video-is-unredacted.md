# Run video is captured unredacted

A Run may be captured to video (`Flow.contingency.video`, or `--video`), using the browser's session-scoped WebM recording. Capture is **not** suspended while a Step enters a secret value. Video therefore contains secrets in plaintext — a 2FA code, an API key, or any credential typed into a field that is not `type="password"` is rendered on screen and written to the file — while `run.json` redacts those same values.

This is accepted rather than solved, because the alternatives were worse for now: masking a target's bounding box relies on a selector that may be stale, and a mis-computed box leaks the credential anyway. Segmenting capture around secret-bearing Steps remains available later; it is cheap, since a fill Step is sub-second.

## Consequences

- `--video` warns when the Flow declares any Variable with `secret: true`, and the segment manifest records `containsSecrets: true` so a future upload adapter refuses by default rather than shipping credentials to object storage.
- Recording adds overhead to the machine under measurement, inflating LCP and INP and widening run-to-run variance. Measurement is unthrottled ([ADR 0008](./0008-performance-is-a-navigation-step-toggle.md)), so that overhead lands directly in the reported numbers rather than being absorbed by a device model.
- **Capture is not segmented around measured navigations.** The calibration experiment for [issue #25](https://github.com/akshat-OwO/contingency/issues/25) measured the cost on a fixed local page, ten Runs per condition, comparing pairs where both conditions reported a metric. INP is consistently higher under capture, by 8ms on one pass and 24ms on another against medians near 144ms. LCP shows no consistent penalty at all — it moved by -8ms on one pass and +4ms on another, so the sign is not stable — though a captured Run occasionally pays a much larger one-off, painting at ~570ms against a ~76ms median. Segmenting would not recover either. The INP cost lands on interactions, which happen after the navigation a segment would end, and stopping and restarting a capture rebuilds the browser context — which drops `localStorage`, so a segmented Run would log itself out of the site mid-Flow. The overhead is instead handled where it can be: a Run records whether it was captured, so a comparison can refuse to weigh a recorded Run against an unrecorded one.
- **Capture replays the Flow in a fresh browser context, and no init script can reach it** — verified against the bundled binary: the `--init-script` flag on `record start` and on later commands does not register in the recording context, the `AGENT_BROWSER_INIT_SCRIPTS` environment variable covers only the context a session opened with, and there is no `addinitscript` command. A captured Run that measures therefore registers its Core Web Vitals recorder by evaluating it into each page it arrives at, before any Step interacts with that page. This loses nothing: paint, shift, and navigation entries replay through `buffered: true`, and a page's only interactions are the Runner's own Steps. An uncaptured Run keeps arming through the session's init script, which also covers navigations the Runner does not model.
- **The recorder performs the Flow's first navigation in a captured Run**, by being handed that Step's URL. A capture that starts on a blank page and navigates afterwards records nothing about three times in five, and a navigation issued the instant `record start` returns loses the capture outright — five times in five without a pause. Arming does not depend on who navigates: paint, shift, and navigation entries replay through `buffered: true`, so a page the recorder opened is measured just as well as one the Runner opened. Measured on this design, five Runs each: a recording written five times out of five, with vitals collected in all five. A capture with no opening URL to hand it — a Flow whose first Step does not navigate — instead waits out the attach on the blank page before the Run proceeds.
- Whether video was captured is recorded in the Run, so Baseline comparison can flag a recorded-versus-unrecorded comparison.
- The recording lifecycle is owned by a scoped finalizer: an unflushed file is a lost file, and the Runs whose video matters most are the ones that abort. Each retry attempt stops the previous recording and produces its own labeled file.
- **Teardown is bounded, and the manifest always accounts for the recording.** A finalizer runs uninterruptibly, so whatever teardown costs is exactly how long Ctrl-C appears to do nothing. The browser tool runs one command at a time per session, so flushing a recording queues behind any command still in flight and waits for that command's own timeout — verified against the bundled binary at 26 seconds against 0.1 on an idle page, and nothing Contingency can send jumps that queue. A Run interrupted mid-Step therefore exits in about a fifth of a second with its video intact, while one interrupted mid-navigation gives up on the file after a few seconds and records why. Holding a terminal for half a minute is the worse failure.
- Video is retained indefinitely until an upload adapter exists. Disk growth is currently the operator's problem.
