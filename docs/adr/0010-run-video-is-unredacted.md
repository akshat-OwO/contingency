# Run video is captured unredacted

> Amended by [ADR 0014](./0014-artifacts-are-run-properties.md). The stance below — artifacts are unredacted, treat them as credentials — holds and now extends to traces. The operational consequences describing live WebM capture no longer apply: video is derived from the trace.

A Run may be captured to video (`Flow.contingency.video`, or `--video`), using the browser's session-scoped WebM recording. Capture is **not** suspended while a Step enters a secret value. Video therefore contains secrets in plaintext — a 2FA code, an API key, or any credential typed into a field that is not `type="password"` is rendered on screen and written to the file — while `run.json` redacts those same values.

This is accepted rather than solved, because the alternatives were worse for now: masking a target's bounding box relies on a selector that may be stale, and a mis-computed box leaks the credential anyway. Segmenting capture around secret-bearing Steps remains available later; it is cheap, since a fill Step is sub-second.

## Consequences

- `--video` warns when the Flow declares any Variable with `secret: true`, and the segment manifest records `containsSecrets: true` so a future upload adapter refuses by default rather than shipping credentials to object storage.
- Recording adds overhead to the machine under measurement, inflating LCP and INP and widening run-to-run variance. Measurement is unthrottled ([ADR 0008](./0008-performance-is-a-navigation-step-toggle.md)), so that overhead lands directly in the reported numbers rather than being absorbed by a device model.
- **Capture is not segmented around measured navigations.** The calibration experiment for [issue #25](https://github.com/akshat-OwO/contingency/issues/25) measured the cost on a fixed local page, ten Runs per condition, comparing pairs where both conditions reported a metric. the estimate is the median difference within a pair, which is what a paired design measures — subtracting one condition's median from the other's discards the pairing and, on these samples, overstated the INP cost by a third. Capture costs about **8ms of INP** against medians near 140ms, the same on both passes. **LCP shows no penalty worth acting on**: the per-pair median moved 0ms on one pass and 4ms on the other, inside the spread of the differences themselves. A captured Run does occasionally pay a much larger one-off, painting at ~570ms against a ~76ms median. Segmenting would not recover either. The INP cost lands on interactions, which happen after the navigation a segment would end, and stopping and restarting a capture rebuilds the browser context — which drops `localStorage`, so a segmented Run would log itself out of the site mid-Flow. The overhead is instead handled where it can be: a Run records whether it was captured, so a comparison can refuse to weigh a recorded Run against an unrecorded one.
- **Capture replays the Flow in a fresh browser context, and no init script can reach it** — verified against the bundled binary: the `--init-script` flag on `record start` and on later commands does not register in the recording context, the `AGENT_BROWSER_INIT_SCRIPTS` environment variable covers only the context a session opened with, and there is no `addinitscript` command. A captured Run that measures therefore registers its Core Web Vitals recorder by evaluating it into each page it arrives at, before any Step interacts with that page. This loses nothing: paint, shift, and navigation entries replay through `buffered: true`, and a page's only interactions are the Runner's own Steps. An uncaptured Run keeps arming through the session's init script, which also covers navigations the Runner does not model.
- **Capture is blank-page-only: every recording starts before the Flow's first navigation, which the Runner itself performs.** An earlier design handed the Flow's opening URL to `record start`, so the browser tool's capture performed that navigation itself — and lost it: frames only arrive on repaint, the recorder's navigation completes before the screencast attaches, and a navigate-first Run produced a hollow recording of its end state. Reproduced against the bundled binary v0.33.2: handing the URL to the capture yielded 3 frames over ~0.3s of final typed state only; starting the capture on a blank page, waiting out the attach settle, and letting the Flow's own navigate Step execute on camera yielded 12 frames over ~1.2s including the load. Every pre-existing guard passed on a hollow recording — file present, >1KB, EBML magic, `recorded: true`, no error — which is why the defect shipped unnoticed; the integration suite now decodes the WebM and asserts a duration floor a hollow recording cannot meet. The attach settle applies to every capture for the same reason: a navigation issued immediately after `record start` left the encoder with nothing five times in five, while one issued after the settle recorded every time. Because the first navigate Step now always executes as a Step, `run.json` reports its true duration instead of folding it into the capture's opening hand-off.
- **The blank page is painted before the Run navigates, because an idle encoder can wedge the flush.** The recorder polls screenshots onto a real-time `ffmpeg` pipe; on a page that never paints, the poll can block across the Flow's opening navigation, and `record stop` then waits out a ~30s internal timeout — against the milliseconds it takes when frames have been flowing — which a captured Run cannot wait out without missing its own five-second flush ceiling. Writing one line of text into the blank page as the capture starts gives the encoder a frame immediately and keeps the flush fast in the overwhelming majority of Runs. The residue of this defect is accepted rather than solved here: it lives in the bundled binary (fixed upstream by replacing screenshot polling with screencast), and a Run that hits it loses its recording with the reason recorded in `video.json` rather than hanging or failing.
- Whether video was captured is recorded in the Run, so Baseline comparison can flag a recorded-versus-unrecorded comparison.
- The recording lifecycle is owned by a scoped finalizer: an unflushed file is a lost file, and the Runs whose video matters most are the ones that abort. Each retry attempt stops the previous recording and produces its own labeled file.
- **Teardown is bounded, and the manifest accounts for the recording wherever Effect can reach.** A finalizer runs uninterruptibly, so whatever teardown costs is exactly how long Ctrl-C appears to do nothing. The browser tool runs one command at a time per session, so flushing a recording queues behind any command still in flight and waits for that command's own timeout — verified against the bundled binary at 26 seconds against 0.1 on an idle page, and nothing Contingency can send jumps that queue. A Run interrupted mid-Step therefore exits in about a fifth of a second with its video intact.
- **A Run interrupted mid-navigation loses the recording, and the process is force-exited.** Verified against the bundled binary: when the signal lands while a navigation — including the Flow's own first, which every captured Run performs on camera — is still in flight, unwinding never completes at all — teardown's own commands (the flush, the load stop, the close) queue behind that navigation, and the fiber parked on a child-process await never processes its Effect-level timeouts, so the CLI used to hang indefinitely until killed. The CLI now bounds this below Effect: commands already in flight when the signal arrived are force-killed six seconds later, which unblocks the queue, and a hard exit at twenty-five seconds backstops whatever remains. The recording is lost either way — and even the manifest cannot be written, because every command that would record why queues behind the same jammed navigation. That is why enabling video warns up front that interrupting mid-navigation may lose the recording: at Ctrl-C time it is too late to say anything. Holding a terminal indefinitely is the worse failure.
- Video is retained indefinitely until an upload adapter exists. Disk growth is currently the operator's problem.
