# Emulation belongs to the Flow

Browser emulation — viewport, user agent, geolocation, website permissions, locale, timezone, and color scheme — is a field on the Flow, applied identically by Create View and by every Run. [Issue #4](https://github.com/akshat-OwO/contingency/issues/4) had scoped geolocation as a Create View control held in process memory, which lets an author _build_ a location-dependent Flow that then cannot be _run_: a headless CI Run would execute it from wherever the CI machine appears to be. Since the CLI is the sole Runner ([ADR 0002](./0002-cli-is-the-sole-runner.md)), emulation belongs to the artifact the Runner reads.

## Consequences

- **Emulated coordinates and permission state are independent.** A site receives the declared coordinates when the Flow grants geolocation access. With an explicit denial, the same coordinates remain installed but the site observes denied permission, which lets an author test refusal deliberately rather than making every location override an automatic grant.
- **Emulation fields** include `viewport`, concrete browser identity, `geolocation`, `permissions`, `locale`, `timezoneId`, and `colorScheme`. Locale and timezone accompany geolocation because a site that geolocates to Berlin and renders US date formats is a bad emulation. `colorScheme` earns its place because accessibility Audits differ under dark mode. `offline` and `extraHTTPHeaders` are deferred; headers overlap with Variables and secrets.
- **Permission decisions are explicit grants or denials**, with origin as an optional key. Create View owns these decisions because Chromium's native permission bubble sits outside the streamed page and cannot be operated or replayed reliably. An absent decision is not treated as a portable prompt. Runs apply the saved answer without UI.
- **A mobile browser identity is coherent, not a user-agent string pasted over a desktop browser.** The Flow stores the concrete signals Create View applied: user agent and client-hint metadata, mobile device metrics, touch capability, viewport, and device scale factor. Create View's named profiles are authoring conveniences and do not become durable Flow references whose meaning could change later. Selecting a mobile profile applies its matching viewport defaults; an explicit viewport edit afterwards wins.
- **Profiles promise only identities Chromium can reproduce.** Create View offers Chromium-family and crawler profiles, and removes Safari and Firefox labels that could only disguise Chromium with a string. Supporting those engines means reopening [ADR 0016](./0016-runs-are-chromium-only.md), not adding a more convincing spoof.
- **Known older Chromium-family profiles migrate to their concrete identity.** Existing Flows whose user-agent strings match a supported built-in profile gain that profile's mobile and touch signals when decoded. The normalized shape stays in memory until the author next finishes or saves the Flow; merely opening a file never rewrites it. Unknown custom strings remain desktop identities until their Flow declares the extra signals explicitly, because guessing from fragments such as `Mobile` is not a durable migration rule.
- **Older Safari and Firefox strings remain legacy overrides.** They continue to run on Chromium with a compatibility warning, but Create View no longer offers them as identities for new work. They are not mapped to a Chromium profile, which would change what the Flow says, and they are not rejected, which would break a runnable artifact.
- **Create View applies Emulation as one snapshot before navigation.** Controls may be set before a browser session or URL exists, but the first request and document receive exactly the configuration shown when navigation begins. Changing browser identity after a page has opened reapplies the complete identity and reloads the current URL while retaining the session's cookies and storage. Recording locks these controls, so the reload never becomes an unrecorded change inside an active Recording.
- **Applying coordinates asks what permission state to author.** When no matching geolocation decision exists, Create View prompts with `Apply and grant location`, `Apply without permission`, and `Cancel`. Applying without permission records a denial rather than leaving Chromium in its inaccessible prompt state. A grant defaults to the current origin and offers an explicit context-wide alternative; before any origin exists, only the context-wide choice is possible and is named plainly. A confirmed decision remains in the Flow until the author removes it, even if coordinates later change or are cleared. Runs never prompt: they reproduce the saved answer.
- **Issue #4 is rewritten, not implemented.** Roughly a third of its thirty user stories existed only to narrate `agent-browser` limitations — that emulation does not grant permission, that an override survives until the session closes, that a Disable control would be misleading, that "disabled" means Contingency never applied anything. Every one of those constraints disappears. [PR #5](https://github.com/akshat-OwO/contingency/pull/5) stays open as a reference for the UI shape and is not merged.
- **A user-agent change no longer risks losing other emulation.** Under `agent-browser` the user agent was launch configuration with a relaunch risk; in Playwright it is a context option, so the full emulation state is rebuilt in one place.
