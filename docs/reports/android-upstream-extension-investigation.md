# Using agent-device without a fork

The current first milestone is [experimental Android with stock agent-device](android-experimental-scope.md). Upstream extensions and private text customization do not gate that smaller scope. This investigation records options for later features that need the complete contract. Prefer upstream support before committing to a helper fork for those features. No complete supported configuration currently closes all of the full-contract gaps.

This source investigation inspected the installed 0.21.25 API and release source `9dabb5b11bf030a8fc0b475dc99ba4718abeca32`, then the latest release reported by GitHub on 2026-10-13, 0.21.27 at `50e45f11bc6d388d272e672771acc33d9e56921d`. The relevant text dispatch, IME transport, Android SDK exports, and plugin documentation are unchanged between those release pins. This follow-up adds no live device coverage and does not change the earlier emulator receipt.

## What can already be reused

The internal `AndroidAdbProvider.text` callback lets a provider supply its own text transport. `fillAndroid` calls that callback once, verifies the result, and returns before the stock IME and shell retry branches. This could avoid both secret-bearing ADB arguments and automatic text retries. It does not itself guarantee privacy; the supplied provider must implement a safe transport and evidence handling. See [text dispatch](https://github.com/callstack/agent-device/blob/50e45f11bc6d388d272e672771acc33d9e56921d/packages/platform-android/src/text-input.ts) and [provider contract](https://github.com/callstack/agent-device/blob/50e45f11bc6d388d272e672771acc33d9e56921d/packages/platform-android/src/adb-transport.ts).

That callback is an internal daemon configuration point. `agent-device/android-adb` exports the provider type and utilities, but not `withAndroidAdbProvider` or a way to configure the built-in local daemon's provider through `createAgentDeviceClient`. Passing a custom client transport changes host-to-daemon RPC delivery, not the daemon's device text implementation. See [SDK exports](https://github.com/callstack/agent-device/blob/50e45f11bc6d388d272e672771acc33d9e56921d/src/sdk/android-adb.ts) and [request provider composition](https://github.com/callstack/agent-device/blob/50e45f11bc6d388d272e672771acc33d9e56921d/src/platform-runtime/request-providers.ts).

This corrects the earlier claim that adaptation necessarily requires a larger backend fork. An internal implementation path already exists. Making it a supported external configuration point could be substantially less maintenance, but that change has not been implemented or accepted upstream.

## Existing public extensions do not finish the job

Provider plugins are experimental and add their own device runtime and platform operations. They cannot replace bundled providers. A Contingency provider could own safe operations, but that is a new backend implementation, not a small decorator around local Android. It would still require lifecycle, capture, action, and compatibility work. There is no documented external operation that wraps the existing local Android runtime wholesale. See [plugin contract](https://github.com/callstack/agent-device/blob/50e45f11bc6d388d272e672771acc33d9e56921d/website/docs/docs/plugins.md).

The daemon's HTTP auth hook can deny an incoming request. Its policy file can restrict serials and command names, including batch and replay admissions. Those are useful outer checks. They do not bind a tap to a screenshot or recheck the focused window at each device-side action. Request admission occurs before command execution and internal recovery. Some recording paths can dismiss an app-owned blocking dialog internally. See [HTTP admission](https://github.com/callstack/agent-device/blob/50e45f11bc6d388d272e672771acc33d9e56921d/src/daemon/server/http-server.ts), [policy documentation](https://github.com/callstack/agent-device/blob/50e45f11bc6d388d272e672771acc33d9e56921d/website/docs/docs/remote-proxy.md), and [dialog recovery](https://github.com/callstack/agent-device/blob/50e45f11bc6d388d272e672771acc33d9e56921d/src/daemon/android-system-dialog.ts).

The new `fill --text-stdin` avoids the CLI's own text argument. The Node API already avoids that CLI hop. Neither changes Android's downstream IME broadcast, whose base64 text still becomes an ADB argument. Upstream [issue 3260](https://github.com/callstack/agent-device/issues/3260) is completed; it must not be counted as an Android device-transport fix. See [release command documentation](https://github.com/callstack/agent-device/blob/50e45f11bc6d388d272e672771acc33d9e56921d/website/docs/docs/commands.md) and [IME broadcast implementation](https://github.com/callstack/agent-device/blob/50e45f11bc6d388d272e672771acc33d9e56921d/packages/platform-android/src/ime-helper.ts).

There is no public local-client retry-policy option in these releases. A global prohibition on retries would be too broad: the ADB executor retries a proven pre-dispatch offline refusal, which does not repeat an action. Contingency needs to prevent repetition after an action may have reached the device. The provider text branch already avoids the stock fill retry loop; all other mutating paths still need dispatch-level review. See [ADB refusal retry](https://github.com/callstack/agent-device/blob/50e45f11bc6d388d272e672771acc33d9e56921d/packages/platform-android/src/adb-provider-scope.ts).

Upstream [issue 2289](https://github.com/callstack/agent-device/issues/2289#issuecomment-6077557802) discusses private secure-field comparison and remains deferred pending transport, target binding, and ownership of its contract. That discussion supports exploring upstream changes, but it is not a commitment to Contingency's required interface.

## Concrete upstream-first work

The upstream issue search found relevant history. [Issue 479](https://github.com/callstack/agent-device/issues/479) requested stable daemon embedding and complete Android provider APIs. It was closed as completed by [PR 481](https://github.com/callstack/agent-device/pull/481), which explicitly removed the public daemon embedding and scoped-provider exports while expanding internal provider routing. This is a deliberate API decision, not an overlooked export. A new proposal must justify a narrow local Android extension and must not assume upstream will reopen general daemon embedding.

[Issue 539](https://github.com/callstack/agent-device/issues/539) completed provider-native Android text injection for remote sessions. Reuse that mechanism rather than propose it again. [Issue 2289](https://github.com/callstack/agent-device/issues/2289) remains open for private secure-field comparison, but is deferred and does not supply the required transport. [Issue 3471](https://github.com/callstack/agent-device/issues/3471) remains open for stale taps on moving Android targets. Its stability guard is relevant, but is narrower than caller-supplied authorization and observation-bound coordinate input. Searches did not find an exact open issue for those combined dispatch requirements. [Issue 3260](https://github.com/callstack/agent-device/issues/3260) is completed CLI stdin work, not work to duplicate.

Start with a bounded design and prototype for these requirements:

1. Expose a supported local Android provider configuration using the existing request-scoped provider mechanism. Keep host and serial binding, cancellation, and cleanup explicit. Avoid imports from unexported source paths or patched package files.
2. Supply private text through an authenticated, bounded device transport. A single callback invocation must not hide repeated commits. Field identity, focused owner, helper session, and observation binding must reach that operation. Preserve meaningful public semantic names while redacting supplied Variable values from output and diagnostics.
3. Add optional observation-bound dispatch checks at the actual mutation points. They must cover semantic and coordinate input, app launch, private input, and internal recovery actions. Refuse missing support, stale evidence, ambiguous ownership, and unauthorized system-dialog actions before further input.
4. Preserve installation authority and helper lifecycle. Contingency must grant installation or replacement explicitly and own its session resources through Effect. Any proposal that changes ADR 0058's Contingency-owned protocol contract requires a maintainer decision, rather than treating an auth hook as equivalent.

Acceptance requires proving that the released public API can configure these mechanisms without private imports; generated sentinel text avoids plain and encoded command arguments and diagnostics; a denied dispatch produces no input; stale targets fail; ambiguous failures invalidate observations without replay; and only owned helper, forward, and IME state is cleaned up. Reuse the earlier Pixel_9 scenarios and keep all unproved device cases separate.

This is a plausible contribution path, not an effort estimate or a claim that the changes are small. Successful upstream acceptance would let Contingency pin normal releases and maintain its own adapter instead of a helper fork. If the upstream contract is declined or cannot satisfy those checks, reconsider the narrow helper fork with its concrete maintenance cost. Do not ship unsafe input while waiting.

No upstream issue, comment, or pull request was posted in this investigation. No package was upgraded, emulator started, or secret supplied. The current decision is to defer the fork commitment and use stock agent-device for the experimental scope. Pursue the upstream work only when a deferred feature needs it, with the original fork handoff retained as a conditional fallback.
