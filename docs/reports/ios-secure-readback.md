# iOS secure text entry and readback research

The available evidence does not establish private entry and exact readback for an arbitrary, unmodified iOS app. Contingency must continue to refuse private fills on iOS under [ADR 0066](../adr/0066-ios-simulator-is-the-next-platform-runtime.md). This is an evidence gap, not a proof that no simulator-only mechanism can work. The requested new live experiments have not been completed.

The [previous spike](ios-private-text.md) demonstrated both sides of the difficulty on iOS 26.5. A fixture independently hashed the actual `UITextField.text` and matched the input, but XCTest exposed only a mask in the snapshot. Stock agent-device returned the full input in its response, and XCTest persisted a fragment in its activity logs and Xcode diagnostics. Mask length cannot prove exact equality. The [evidence](ios-secure-readback-evidence.json) distinguishes those earlier observations from this investigation.

## Candidates

| Rank | Candidate | Entry and verification | Assessment and maintenance |
| --- | --- | --- | --- |
| 1 | Simulator HID input plus injected in-process comparator | HID can avoid `typeText` activity generation in principle. An injected helper could compare the actual field content in the app process and return a boolean. Neither privacy nor exact readback has been proven here. | Highest-value experiment for ordinary UIKit fields. Requires a version-checked private HID protocol and injection, a secure request channel, field binding, and fail-closed behavior. SwiftUI, web views, custom controls, process relaunch, and apps that reject injection remain open. |
| 2 | Cooperating app hook | A purpose-built app can compare its own field content and return only a verdict. Entry still needs a separately audited path. | A narrower fallback requiring app changes and an authenticated hook. The existing fixture's hash receipt is evidence of fixture cooperation, not a general implementation. |
| 3 | Private XCTest synthesis and snapshots | Avoiding activity logging might make entry private. The tested XCTest snapshot returned a mask for the secure field; direct `XCUIElement.value` was not independently tested here; no private snapshot exposing exact content has been demonstrated. | Requires testing activity suppression and every diagnostics channel, plus private XCTest compatibility per Xcode version. Suppressing one activity does not prove other logs are clean. |
| 4 | Host or simulator accessibility | Host AX, AXRuntime, and `accessibilityValue` may expose app-provided accessibility data. No exact secure value has been established. | An app may mask or customize its accessibility representation. A returned string must not be assumed to be the underlying field content. |
| 5 | Simulator pasteboard | `simctl pbcopy` accepts stdin, avoiding a text argument. Pasting requires a separate input action and leaves the value on the shared simulator pasteboard until replaced. | Reject for private fills without a separate privacy design and audit. It does not independently establish exact field content. |
| 6 | Stock agent-device and XCTest `typeText` | The prior sentinel test found a full response echo and persisted fragments, despite exact fixture-assisted readback. | Reject as currently implemented. Redacting the response cannot remove XCTest diagnostics. |

The [idb simulator control implementation](https://github.com/facebook/idb/tree/main/FBSimulatorControl) describes direct keyboard events through private Simulator HID services. This is a candidate for entry, not evidence that a particular secret entered through those services stays out of logs or lands exactly. `simctl launch` accepts environment variables prefixed with `SIMCTL_CHILD_`; this makes `DYLD_INSERT_LIBRARIES` worth testing without putting the secret in the environment. The library path and any authentication metadata are still exposed to the process environment, so they must not contain the secret. Injection can alter application behavior even when the app bundle is unchanged. ADR 0066 does not explicitly decide whether runtime injection satisfies its Target App boundary. A production choice needs an explicit design decision and must refuse when injection, field identity, or exact comparison cannot be established.

An injected UIKit comparator must bind the intended field rather than selecting an arbitrary first responder, compare the actual string against the requested value in process, and return only a verdict. A successful equality result is meaningful only if the helper has identified the same field observed by the automation and the app has finished processing the edit. A custom widget may not use `UITextField`; SwiftUI's implementation is not a stable public UIKit contract. Hash equality is useful for a fixture receipt, but production can compare the value internally without returning a hash.

## Scope and next proof

Xcode 27.1 build 27A9275 and simulator runtimes iOS 26.5 and 27.1 were present during this investigation. No new simulator was booted, no new secret was entered, and no new privacy audit was run. Consequently, neither runtime has a new HID or injection result, and no SwiftUI `SecureField` result exists. The earlier iOS 26.5 XCTest proof does not cover iOS 27.1 or the candidate mechanisms.

The next experiment must create its own simulator, install a public fixture with both a UIKit secure field and a SwiftUI `SecureField`, and send a random sentinel through a mode-0600 file or stdin. It must independently compare the actual value, including a same-length mismatch, and audit full values and fragments in sampled arguments, host and simulator unified logs, XCTest diagnostics, and crash reports. Record only the hash, length, and sanitized outcomes. Test both installed runtimes separately and delete only the experiment's simulator and resources. A passing fixture is still not a guarantee for arbitrary apps.
